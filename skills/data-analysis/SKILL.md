# Data Analysis

## 目标

基于实际数据回答用户的分析问题，识别有业务意义的趋势、差异、结构、异常和潜在问题。分析不止复述数值，还要说明发现为何重要、证据支持到什么程度，以及仍有哪些未知。

## 适用条件

- 用户提供了数据、查询结果或可访问的数据集。
- 需要分析趋势、对比、构成、分布、异常或指标变化。
- 需要先判断数据质量是否会影响结论。
- 已有初步指标，希望继续下钻并解释其业务含义。

只有数据库结构、尚无数据时，先使用 `database-exploration`。已有结论只需整理成正式材料时，使用 `report-generation`。

## 职责边界

本 Skill 负责数据质量评估、分析方法选择、指标计算、结果解释和洞察形成。不负责在陌生数据库中自行寻找数据，也不负责正式报告的完整排版。它不提供统计计算能力本身：计算、清洗或绘图必须依靠当前会话实际提供的 Tools。当前会话存在 `run_python_analysis` 时，可将其用于 SQL 不适合表达的精确统计计算；该工具是本地可信开发环境中的受限执行器，不是可安全执行任意不可信代码的沙箱。

如果没有计算 Tool，只有在用户提供的数据足够小、计算步骤可直接核验时，才进行透明的手工计算；应展示公式或中间值。对于大数据、复杂统计或无法核验的计算，说明限制并请求计算结果或可用工具。不得伪造精确统计值。

## 工作原则

### 核心规则

以下规则优先于其他分析习惯：

1. 精确计算优先由 SQL 或实际可用的计算 Tool 完成。不要依靠阅读大量明细数据进行心算、排序、比例计算、相关性计算或距离估算。
2. 未实际执行的查询或计算，不能写成已经验证的发现。可以提出分析方法，但必须明确标记为待验证的方法或分析建议。
3. 只有查询结果覆盖目标总体，或者采用了明确、合理的抽样方法，才能形成总体结论。少数案例、Top/Bottom 样本和人工挑选的记录不能直接代表整体规律。
4. 相关关系、组间差异和预测特征不能直接表述为因果关系。没有足够因果证据时，只能描述为关联或观察现象。
5. 每项核心事实性结论必须能够由真实 Tool Result 或实际计算结果支持。证据不足时，应降低结论强度、标记为假设或省略；不得为了补充次要结论而执行与用户目标无关的查询。
6. 数据质量结论必须来自实际检查。聚合结果非空不代表原始字段没有 NULL；查询成功不代表数据完整、唯一或合理。

### 通用原则

1. 先定义分析问题和指标口径，再选择方法。
2. 比较变化时同时考虑绝对量、相对比例、基数和样本量。
3. 均值可能被偏态或极端值影响；必要时同时查看中位数和分位数。
4. 缺失值、重复值和异常值不得静默删除或填补，处理方法和影响必须说明。
5. 数据不足时降低结论强度，明确说明不支持哪些判断。
6. 不为了得到显眼结论而忽略反例或与预期不符的数据。

## 分析深度

根据用户问题选择最小但足够的分析深度，不机械执行完整流程。

### 简单事实查询

适用于数量、排名、总和、平均值和列表等问题。

- 优先通过一条明确的 SQL 得到结果。
- 不强制执行完整数据质量分析。
- 不为了展示分析过程而增加无关查询。
- 对少量、已经返回的简单数字，可以直接比较和解释。

### 常规对比分析

适用于不同类别、时间段或群体之间的表现比较。

- 明确比较对象、指标和统计口径。
- 根据结论需要检查样本数量和关键字段质量。
- 同时考虑绝对量、比例和基数，避免只比较单一指标。
- 尽量在 SQL 中完成分组、排序、差值和比例计算。
- 不执行与当前比较无关的全面质量扫描。

### 探索性分析

适用于寻找影响因素、异常规律或潜在问题。

- 根据用户目标提出合理的候选假设，并优先选择最可能影响结论的分析方向。
- 每项重要假设必须通过实际查询或计算验证后，才能升级为事实性发现。
- 控制查询数量，优先复用已有查询结果。
- 未验证的解释必须保留为假设，不能写成事实。

### 因果、预测和决策问题

适用于“什么因素导致结果变化”“未来结果是多少”或“应该选择哪一方案”等问题。

- 首先判断现有数据和工具是否支持该问题。
- 没有足够证据时，不给出确定性因果或预测结论。
- 可以提供观察到的关联、数据限制以及进一步验证方案。
- 不得把相关性分析冒充因果分析。

## 计算与工具分工

模型负责理解用户问题、确定分析目标和指标、选择分析方法、决定需要哪些数据，以及解释和归纳计算结果。

SQL 或实际可用的计算 Tool 负责需要精确执行的计算，并按以下边界选择：

- 分组、过滤、排序、排名、总和、计数、均值、占比、变化率、NULL、重复值和样本量等数据库擅长的计算，优先由 SQL 完成。
- 中位数、分位数、相关系数、统计检验以及 SQL 难以清晰表达的数值分析，可在确认分析数据集完整且规模受限后使用 `run_python_analysis`。
- 不要为了展示 Python 能力，把一条简单 SQL 能完成的问题改成导出明细后再计算。
- Python 分析所使用的数据必须来自当前任务实际执行成功的 Tool Result；不得在代码中编造、补写或假定数据库记录。
- Python 返回的相关性、组间差异或统计显著性仍不自动证明因果关系。

- 对少量、已经返回的简单数字，模型可以直接比较和解释。
- 不应让模型通过阅读大量 JSON 明细自行统计或估算。
- 不应把大量明细先通过普通 SQL Tool 返回给模型，再由模型手工计数；需要复杂统计时应直接让实际计算 Tool 处理受限数据集。
- 如果当前工具未提供或不支持某项计算，可以说明计算方法和所需字段，并标记为待验证。
- 不得把目测、猜测或未经执行的计算写成精确统计结果。

## 查询成本与效率

1. 优先复用当前任务已有的 Tool Result 和查询结果。
2. 一条 SQL 能完成的多个相关计算，尽量合并执行。
3. 只有缺失信息会影响当前结论时，才继续查询。
4. 不为无关的潜在问题执行额外检查。
5. 如果证据不足，可以降低结论强度或说明限制，不必为了得到更确定的结论无限追加查询。
6. 不要求每个结论都经过第二次模型审核。
7. 不要求每次分析都执行固定的数据质量检查流程。

## 工作流程

### 1. 明确分析问题

确认用户要解释的现象、比较对象、时间范围、核心指标，以及结果用于描述、诊断还是决策。把宽泛目标拆成可检验的问题。例如“销售表现如何”可以拆成销售额和订单量趋势、主要贡献维度、下滑或增长发生的时间，以及客单价或购买量的变化。

### 2. 判断分析深度

判断任务属于简单事实查询、常规对比、探索性分析，还是因果、预测和决策问题。选择与问题相称的流程；简单查询可以跳过不必要的数据画像、质量检查和方法说明。

### 3. 确认数据和口径

记录数据来源、时间范围、每行数据的粒度、指标定义、过滤条件、单位、币种和时区。确认数据是明细、抽样还是汇总。若来源间口径不同，不直接拼接或比较；先说明差异并选择可比范围。

同时判断当前任务已有的数据和查询结果是否足以回答问题。已有证据足够时直接复用，不重复查询。

### 4. 按需检查数据质量

只检查可能影响当前结论的数据质量问题，不为了形式完整执行全面扫描。根据目标选择检查：

- 关键字段的 NULL 数量和比例。
- 分析对象的实际样本数量。
- 主键或业务键是否重复。
- 时间字段是否存在断档、统一填充值或异常范围。
- 数值字段的最小值、最大值和明显不合理值。
- JOIN 前后行数是否因一对多关系发生膨胀。
- 聚合函数是否因 NULL、重复记录或过滤条件改变统计口径。

可以将多个相关质量指标合并到同一条 SQL 时，优先合并。已有查询结果能够支持判断时，不重复查询。没有实际检查时，不得声称不存在 NULL、重复值或异常值。

仅凭数值大或小不能判定错误。异常值可单独分析，不能擅自删掉。

### 5. 决定数据处理方式

根据检查结果选择保留、标记、排除、去重、分组处理或适当填补。对关键指标，缺少业务依据时不填补。说明处理规则、涉及记录数、选择理由，以及处理前后结果是否改变。必要时并列展示处理前后的分析结果。

### 6. 选择最少但足够的查询或计算

优先让 SQL 或实际 Tool 完成精确计算，并尽量将同一问题的相关指标合并查询。简单聚合优先 SQL；只有分析确实需要中位数、分位数、相关系数、统计检验或其他 SQL 不适合的计算时，才使用 `run_python_analysis`。只有现有结果不足以支持当前核心结论时，才追加查询。

对于需要了解整体分布或检查口径的任务，可以建立基础画像，包括数据规模和时间跨度、核心指标总量、均值、中位数、范围、必要分位数、主要类别数量与占比。简单事实查询不必强制建立画像。

### 7. 按问题选择方法

- **趋势分析**：观察方向、环比或同比、拐点及周期性；检查时间断档和口径变化，并按相关维度下钻变化来源。
- **对比分析**：比较绝对差异和相对变化；检查样本规模、基准值、群体构成和比较条件是否一致。
- **分布分析**：查看中位数、分位数、偏态、离散程度和长尾；分布偏斜时不只用均值代表典型情况。
- **构成分析**：分析占比、贡献者、集中度及构成随时间的变化；区分总量变化和组成变化。
- **异常分析**：定位突增、突降或离群点，再检查时间、群体、数据质量和可能事件。异常只是值得调查的信号，不自动证明原因。
- **下钻分析**：仅在总体发现需要解释时，按时间、地区、产品、客户、渠道或其他相关维度逐层拆解。

选择与目标相称的方法；没有统计基础时，不使用复杂方法制造精确感。

### 8. 形成与证据强度匹配的发现

每项重要发现应说明数字证据、时间与对象范围、业务含义和局限，并说明分母、基准和单位，特别是百分比变化。证据只支持局部观察时，不得概括为整体规律。

### 9. 结束与交接

保留与用户目标直接相关、影响较大且证据充分的发现。交给 `report-generation` 时提供分析目标、数据范围和口径、数据质量处理、关键发现与数字、建议图表及字段、限制和待验证假设。

以上步骤不是固定流水线。简单查询可以直接从明确问题进入必要查询并回答；复杂分析才逐步展开质量检查、方法选择和假设验证。

## 结论类型

分析过程中区分：

- **事实**：由实际查询或计算直接得到的结果。
- **观察**：数据中看到的模式，但尚未完成充分统计验证。
- **假设**：对现象原因的可能解释，需要更多数据验证。
- **建议**：基于事实和限制提出的后续行动。

不得把观察写成普遍规律，不得把假设写成事实，也不得把建议描述为必然有效。简单事实查询不必在最终回答中强制展示这些标签；复杂分析可以根据实际需要显式区分。

## 方法来源

本 Skill 提供数据分析的工作原则、质量要求和通用流程。具体选择哪些指标、维度、假设和分析方法，应由模型根据用户目标、字段结构和实际数据判断。

不得声称某个具体分析维度由 Skill 强制规定，除非 Skill 正文确实明确要求。

## 输出要求

根据任务复杂度组织回答，不强制套用固定报告模板。

- **简单事实查询**：直接回答用户问题，提供关键数字和必要统计口径，不强制输出分析报告。
- **常规对比和探索性分析**：优先输出少量重要发现，提供关键数字、分析对象、数据范围和必要比较基准；根据需要说明结论属于事实、观察还是假设，并说明会影响结论的限制。
- **复杂分析**：说明核心发现、证据、限制和建议；不堆砌所有查询结果，也不为了满足固定模板重复解释。

若没有执行某项计算，应清楚标明这是方法建议、定性观察或待验证假设，而非已计算结果。

## 质量检查

- 分析回答了用户提出的问题，而非只输出通用汇总。
- 分析深度与问题复杂度相称，没有执行无关查询。
- 在结论确实依赖数据质量时，已检查相关字段和样本范围；未检查的事项没有被表述为已确认。
- 如处理了缺失、重复或异常，处理规则和影响透明。
- 变化结论同时考虑了绝对量、比例和基数。
- 每项核心事实性结论都有可核验的 Tool Result 或实际计算结果和口径。
- 没有通过少数案例、Top/Bottom 样本或人工挑选记录概括整体规律。
- 区分事实、观察、假设与建议。
- 没有夸大因果关系、编造计算、隐藏不确定性或把未执行的方法写成已验证结果。
- 已优先复用现有结果，并将可以合并的相关计算尽量合并。
